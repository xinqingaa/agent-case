# 详细版文档蓝图

## 1. 设计思路

详细版不是 15 篇互不相关的文章，而是一条从产品到实现、从理解到验证、从学习到表达的证据链。

```mermaid
flowchart LR
    Product[01-02 产品] --> System[03-06 环境与架构]
    System --> Data[07 数据与状态]
    Data --> Flow[08 核心链路]
    Flow --> Code[09 关键代码]
    Code --> Quality[10-12 集成、测试、风险]
    Quality --> Learn[13-14 练习与面试]
    Learn --> Guide[00 学习导航最后回填]
```

## 2. 文档分组

| 分组 | 文档 | 核心问题 |
|---|---|---|
| 学习入口 | `00` | 应该按什么顺序学，学到什么程度？ |
| 产品事实 | `01`、`02` | 谁使用、解决什么问题、真实链路是什么？ |
| 系统地图 | `03` 至 `06` | 如何运行、由什么组成、入口和边界在哪里？ |
| 实现主线 | `07`、`08`、`09` | 数据如何变化、请求如何流动、哪些代码最关键？ |
| 工程专题 | `10` 至 `12` | 如何与外部协作、怎样验证、风险和取舍是什么？ |
| 学习输出 | `13`、`14` | 如何练习、如何准确表达？ |

## 3. 单篇契约

### `00-learning-guide.md`

- 输入：其余详细文档的稳定结论。
- 输出：知识地图、前置知识、三种学习路径、预计时间、完成标准。
- 编写时机：最后。
- 禁止：先假设核心链路，再强迫后续文档适配。

### `01-project-and-product.md`

- 输入：用户确认、可见入口、需求/说明候选材料。
- 输出：一句话定位、用户、问题、能力、输入输出、明确边界。
- 验收：不用技术名词也能解释项目价值；“企业级”等词有证据或降级为定位。

### `02-product-journeys.md`

- 输入：真实 UI/API/CLI 行为。
- 输出：2 至 4 条用户旅程、正常/异常结果、到代码链路的桥梁。
- 验收：每一步都能映射到入口或核心链路。

### `03-environment-and-runbook.md`

- 输入：清单、配置、入口、运行证据。
- 输出：环境矩阵、变量、依赖、从零启动、成功信号、故障恢复。
- 验收：静态候选与已运行命令严格区分；副作用明确。

### `04-stack-and-dependencies.md`

- 输入：依赖清单和真实导入/调用。
- 输出：关键技术职责、版本约束、运行/开发依赖、选型取舍。
- 验收：不复制完整 lockfile；每个关键依赖都有实际作用位置。

### `05-architecture.md`

- 输入：入口、进程边界、模块依赖、外部系统。
- 输出：系统上下文、模块图、运行时视图、部署候选、架构判断。
- 验收：图中每个节点都能定位；架构标签不靠猜。

### `06-codebase-map.md`

- 输入：目录、入口和稳定模块。
- 输出：带注释树、入口清单、依赖方向、首次阅读顺序和可跳过区域。
- 验收：不是逐文件说明书，能让读者在 10 分钟内定位核心代码。

### `07-domain-and-data.md`

- 输入：状态结构、领域对象、存储模型和生命周期。
- 输出：术语、数据关系、状态机、事务/一致性、敏感数据和隔离。
- 验收：区分请求状态、持久数据、缓存和外部数据。

### `08-core-flow-<name>.md`

- 输入：产品旅程、入口、调用关系、数据变化和测试。
- 输出：顺序图、节点表、状态变化、失败/重试/降级、阅读顺序和验证方法。
- 验收：从触发到用户可见结果闭环；至少一篇。

### `09-key-code-deep-dives.md`

- 输入：核心链路中的高风险/高决策密度符号。
- 输出：职责、调用关系、输入输出、副作用、不变量、边界、修改影响、设计评价。
- 验收：选择依据是链路价值，不是文件长度。

### `10-interfaces-and-integrations.md`

- 输入：API、数据库、队列、外部服务和配置。
- 输出：方向、协议、认证、超时、重试、降级、幂等性和测试替身。
- 验收：每个外部边界都有失败影响和密钥边界。

### `11-testing-and-debugging.md`

- 输入：测试目录、CI、日志、trace 和运行结果。
- 输出：覆盖矩阵、执行命令、调试地图、可观测性和缺口。
- 验收：区分“有测试文件”和“核心行为被断言”。

### `12-quality-risks-and-tradeoffs.md`

- 输入：实现事实、运行观察和未知项。
- 输出：按优先级的安全、正确性、性能、运维和维护风险；设计取舍与改进路线。
- 验收：风险不冒充事故，建议有验证方法，指标不凭空出现。

### `13-learning-exercises.md`

- 输入：稳定架构、核心链路和风险。
- 输出：观察、解释、局部修改、跨模块扩展四级练习。
- 验收：每题有前置、范围、不变量、完成标准和验证方法。

### `14-interview-guide.md`

- 输入：已验收事实、用户确认的个人贡献和运行数据。
- 输出：两分钟/五分钟讲法、高频追问、取舍、不能声称的内容。
- 验收：不把项目已有代码说成个人成果，不使用无证据数字。

## 4. 横向一致性

| 源文档 | 必须同步的下游 |
|---|---|
| 产品链路变化 | 架构、核心链路、练习、面试 |
| 启动命令变化 | 运行手册、测试、练习 |
| 状态/数据变化 | 核心链路、精读、风险 |
| 外部接口变化 | 架构、运行手册、测试、风险 |
| 风险结论变化 | 练习、面试禁用声明 |
| 运行验证变化 | 证据台账、验收、简洁版 |

## 5. 篇幅控制

篇幅由复杂度决定，但每篇只解决自己的核心问题。相同背景通过链接引用，不重复复制。代码片段只保留理解所需的最小部分；优先给路径和符号。

一个简单项目可以只有一篇核心链路，复杂项目可有多篇 `08`。专题不适用时保留 3 至 8 行说明，不用空模板充数。

## 6. 阅读体验标准

- 每篇开头说明前置知识、目标和预计时间。
- 首次出现的术语进入 `GLOSSARY.md`。
- 表格用于精确映射，Mermaid 用于上下文、依赖、状态和顺序。
- 每篇结尾说明完成判定和下一篇。
- 路径、命令、配置键和证据 ID 使用等宽格式。
- 未运行、未确认和推断必须在读者第一眼可见。
