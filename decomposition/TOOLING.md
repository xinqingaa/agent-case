# Skill、SDD 与 MCP 工具路线

## 1. 结论

V1 使用“文档规范 + 模板 + 仓库内 Skill + 小型校验脚本”，暂不自研 MCP。

原因：当前核心问题是把拆解方法、授权、证据和文档契约稳定下来；本地文件搜索、阅读和命令执行已有基础工具。过早建设 MCP 会增加协议、权限、部署和维护成本，却不能自动解决事实质量和学习编排问题。

## 2. Skill 的职责

官方 OpenAI 文档将 Skill 定义为包含指令、资源和可选脚本的可复用工作流，并采用渐进式披露加载内容。这个任务与 Skill 高度匹配，因为拆解方法稳定、项目事实变化。[官方 Build skills](https://developers.openai.com/codex/skills/)

仓库内 `project-learning-decomposer` 应负责：

- 识别完整项目学习拆解任务。
- 强制先读取规范和项目授权卡。
- 按阶段门选择要读的文件和要产出的文档。
- 统一证据状态、核心链路和代码精读标准。
- 调用初始化/校验脚本。
- 在授权边界停止，而不是自行扩大范围。

Skill 不应负责：

- 保存某个具体项目的架构事实。
- 自动把目录名推断为业务职责。
- 默认安装依赖、启动服务或调用外部 API。
- 代替人工评审学习质量和事实准确性。

## 3. SDD 文档模型

这里的 SDD 采用“Specification-Driven Documentation”：先确定拆解规格和验收，再收集证据和写文档。

| SDD 产物 | 当前对应 | 作用 |
|---|---|---|
| 系统规格 | `SPEC.md` | 规定授权、阶段、证据和详细版契约 |
| 项目实例规格 | `project.yaml` | 记录范围、读者、revision、授权和排除项 |
| 证据账本 | `EVIDENCE.md` | 把结论和来源绑定 |
| 文档实现 | `detailed/*.md` | 按契约组织学习内容 |
| 验收规格 | `ACCEPTANCE.md` | 阶段门和阻断项 |
| 派生产物 | `quick/*.md` | 从已验收详细版生成 |

推荐闭环：

```text
规格 -> 授权 -> 证据 -> 详细文档 -> 交叉检查 -> 运行回填 -> 验收 -> 简洁版
```

## 4. MCP 的职责边界

官方 OpenAI 文档将 MCP 定位为把模型连接到第三方工具和上下文，可使用本地 STDIO 或远程 Streamable HTTP server。[官方 MCP 文档](https://developers.openai.com/codex/mcp/)

这意味着 MCP 适合解决“访问什么工具/数据”，不适合代替“应该如何拆解项目”。后者仍属于 Skill 和规格。

### 暂不需要自研 MCP 的场景

- 只读本地源码、清单和文档。
- 使用 `rg` 做文本/符号搜索。
- 执行受控构建、测试和本地命令。
- 写 Markdown、Mermaid 和证据台账。

### 值得引入 MCP 的触发条件

满足至少两个条件再评估：

1. 三个项目重复出现同一类外部系统访问。
2. 需要统一的只读权限、脱敏和审计记录。
3. 需要语义能力，例如 LSP 符号/引用图，普通搜索成本过高。
4. 运行证据分散在浏览器、日志平台、CI 或远程仓库。
5. 多个 Agent/客户端需要共享同一工具契约。

## 5. 可选现成 MCP

| MCP | 适用阶段 | 价值 | 是否必需 |
|---|---|---|---|
| Context7 | 技术栈/依赖解释 | 查询当前框架文档，避免依赖记忆 | 可选 |
| Playwright MCP | L4 UI 验证 | 页面、网络和截图验证 | Web 项目推荐 |
| Chrome DevTools MCP | L4 浏览器调试 | Network、console、性能诊断 | 可选 |
| GitHub MCP | 需要 PR/Issue 语义时 | 补充本地 Git 之外的历史与讨论 | 可选 |
| OpenAI Docs MCP | 构建/维护 Codex Skill 时 | 查询官方 OpenAI 文档 | 工具体系维护可选 |

本地 Git、文件和 shell 已能完成的任务，不因“统一”而强行换成 MCP。

## 6. 未来自研 MCP 草案

暂定名称：`project-evidence-mcp`。只在真实重复需求出现后实施。

### 只读工具

| 工具 | 输入 | 输出 | 安全要求 |
|---|---|---|---|
| `get_project_manifest` | 项目 ID | 语言、清单、入口候选 | 不读 `.env` |
| `list_source_tree` | 项目 ID、深度、排除规则 | 归一化目录树 | 排除依赖/生成/数据目录 |
| `search_symbols` | 查询、语言、范围 | 符号和引用位置 | 返回窄范围，不批量泄露源码 |
| `read_excerpt` | 路径、符号/行范围 | 受限源码片段 | 路径白名单、最大长度 |
| `get_git_context` | 路径/符号 | 提交和变更摘要 | 只读 |
| `validate_evidence` | 证据记录 | 路径/符号是否存在 | 不替代语义审查 |

### 受控运行工具

只在 L4 后开放：

| 工具 | 作用 | 必须记录 |
|---|---|---|
| `run_build` | 执行白名单构建命令 | cwd、版本、退出码、副作用 |
| `run_tests` | 执行白名单测试 | 测试数、失败、环境 |
| `start_service` | 启动本地服务 | 端口、PID、健康信号、停止方式 |
| `capture_http` | 受控请求 | 脱敏请求/响应、外部调用风险 |

### MCP 不应提供

- 任意 shell 命令。
- 默认读取 `.env`、数据库或用户文件。
- 无白名单的递归文件读取。
- 自动提交代码、清理数据或调用生产 API。
- 把推断直接写成 `[V]`/`[R]` 的能力。

## 7. 演进路线

### V1：当前

规范、模板、Skill、初始化脚本、机械校验和人工验收。

### V1.1：首个项目后

补充真实遇到的文档缺口、证据交叉检查和 Skill 触发评测；仍不默认做 MCP。

### V2：三个项目后

统计重复操作的频率、耗时和错误率。只有工具化收益明确，才实现最小只读 MCP；运行工具另立安全评审。

### V3：需要分发时

若 Skill 和 MCP 要给其他人安装，再考虑打包为 Plugin；本仓库内学习使用不需要提前插件化。
