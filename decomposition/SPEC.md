# 项目学习拆解规范

版本：0.1.0  
状态：试行  
适用范围：`code/` 下的完整项目及后续同类项目

## 1. 目标

本规范用于把一个可运行的完整项目转化为可验证、可学习、可复习的详细拆解文档。详细版是唯一事实源；简洁版、面试速记和其他摘要必须从已验收的详细版提炼，不得独立重新分析。

完成后的文档应让缺少项目背景的学习者能够：

1. 理解项目解决的问题、目标用户和主要产品链路。
2. 在明确环境中启动项目，并知道如何判断启动成功。
3. 建立系统边界、模块关系、数据流和运行时流程的整体认识。
4. 按推荐顺序阅读关键代码，而不是从目录第一项开始盲读。
5. 追踪至少一条端到端核心链路，并理解正常、失败和降级路径。
6. 解释重要设计选择、局限和可行改进。
7. 完成由浅入深的练习，并能用自己的语言讲清项目。

## 2. 非目标

- 不以覆盖每个文件、类或函数为目标。
- 不把 README、注释或目录名称直接当作实现事实。
- 不为增加篇幅而复制大段源码。
- 不在未授权时读取、运行或修改原项目。
- 不把推断、宣传性指标或面试话术伪装成已验证事实。
- 不默认重构或修复项目；发现问题只记录证据和影响，除非用户另行授权。

## 3. 核心原则

### 3.1 证据优先

每个非平凡结论必须能够追溯到源码、配置、运行输出、测试结果或用户确认。文档使用以下状态：

| 标记 | 含义 | 使用条件 |
|---|---|---|
| `[R]` | 运行验证 | 已执行命令或操作，并观察到结果 |
| `[V]` | 静态验证 | 已由源码、配置、测试或版本记录支持 |
| `[C]` | 用户确认 | 来自用户提供的项目背景或设计意图 |
| `[I]` | 合理推断 | 有间接证据，但尚未运行或缺少直接实现证据 |
| `[U]` | 未知 | 当前证据不足，必须明确列出待确认项 |

重要结论在句末引用证据编号，例如：`[V][E-ARCH-003]`。同一段落可共用证据，但不得用一个模糊证据支持多个无关结论。

### 3.2 产品链路先于代码目录

先回答用户做什么、系统产生什么价值，再解释这些行为由哪些代码完成。目录结构是导航工具，不是文档主线。

### 3.3 运行事实高于静态猜测

README 中的命令属于候选命令。只有实际执行并记录环境、退出状态和成功信号后，才能标记为 `[R]`。

### 3.4 渐进式学习

每篇文档说明前置知识、阅读目标、预计耗时、学习结果和下一步。首次出现的项目术语进入术语表。

### 3.5 原项目只读优先

拆解产物写入 `decomposition/projects/<project-id>/`。默认不修改 `code/` 下的项目，不生成依赖锁文件，不执行格式化，不写入数据库。

## 4. 授权等级

每个项目在 `project.yaml` 中记录当前授权。操作不得超过已授权等级。

| 等级 | 允许操作 |
|---|---|
| L0 | 不读取 `code/`；只建设规范、模板和计划 |
| L1 | 查看目录、README、清单、配置示例和现有说明文档 |
| L2 | 阅读用户指定的入口、模块和核心链路文件 |
| L3 | 在项目内全局搜索和选择性阅读，排除依赖、构建和生成目录 |
| L4 | 安装依赖、构建、启动、执行测试和本地浏览器验证 |
| L5 | 对本地数据库、队列或外部服务进行明确范围内的只读验证 |

授权升级必须记录日期、范围和限制。L4 不自动包含 L5；允许启动项目也不等于允许写入真实外部系统。

## 5. 分析阶段与阶段门

### G0：范围确认

- 已确定项目路径、项目 ID、目标读者和授权等级。
- 已定义排除目录、禁止操作和敏感信息规则。
- 未满足时不得开始源码分析。

### G1：项目侦察

- 已识别语言、框架、入口、配置、测试和主要边界。
- 已区分源文件与依赖、构建、生成文件。
- 已建立初始证据台账和未知项列表。

### G2：运行基线

- 已记录环境版本和依赖准备方式。
- 已验证或明确标注未验证的启动、测试、构建命令。
- 已定义可观察的成功信号和常见失败恢复方式。

### G3：产品与架构模型

- 已描述目标用户、主要场景、系统上下文和模块边界。
- 架构名称有证据支持；无法证明时只描述观察到的结构。
- 图表中的节点可以映射到真实模块或外部系统。

### G4：核心链路

- 已选择 2 至 4 条代表产品价值或技术特点的链路；简单项目可降为 1 条并说明原因。
- 每条链路覆盖触发、入口、校验、业务逻辑、数据、外部调用、输出和失败路径。
- 关键节点具有路径、符号和证据引用。

### G5：专题与学习化

- 已完成适用的测试、调试、配置、集成、安全、性能和技术债专题。
- 已给出阅读顺序、前置知识、练习和验证方法。
- 面试材料只引用已验收的项目事实。

### G6：最终验收

- 文档之间不存在已知矛盾。
- 证据链接有效，命令结果可复核，未知项未被隐藏。
- `ACCEPTANCE.md` 中所有阻断项已通过或获得明确豁免。

## 6. 详细版文档契约

每个项目的 `detailed/` 默认包含：

| 文件 | 内容 | 要求 |
|---|---|---|
| `00-learning-guide.md` | 学习导航、阅读顺序、知识地图 | 必需 |
| `01-project-and-product.md` | 背景、用户、价值、功能边界 | 必需 |
| `02-product-journeys.md` | 用户场景和产品链路 | 必需 |
| `03-environment-and-runbook.md` | 环境、启动、验证、故障恢复 | 必需 |
| `04-stack-and-dependencies.md` | 技术栈、关键依赖及作用 | 必需 |
| `05-architecture.md` | 系统上下文、边界、模块与部署 | 必需 |
| `06-codebase-map.md` | 目录、入口、模块职责和阅读顺序 | 必需 |
| `07-domain-and-data.md` | 核心概念、数据模型、状态流转 | 适用时必需 |
| `08-core-flow-<name>.md` | 单条端到端核心链路 | 至少 1 篇 |
| `09-key-code-deep-dives.md` | 核心符号精读 | 必需 |
| `10-interfaces-and-integrations.md` | API、事件、数据库、外部系统 | 适用时必需 |
| `11-testing-and-debugging.md` | 测试策略、调试路径、日志 | 必需 |
| `12-quality-risks-and-tradeoffs.md` | 安全、性能、技术债和设计取舍 | 必需 |
| `13-learning-exercises.md` | 分级练习和验证方法 | 必需 |
| `14-interview-guide.md` | 项目表达和追问题库 | 必需 |

项目根目录还必须包含：

- `project.yaml`：范围、授权和项目元数据。
- `EVIDENCE.md`：证据台账。
- `GLOSSARY.md`：术语表。
- `ACCEPTANCE.md`：阶段门和最终验收结果。
- `working/`：临时分析记录，不作为最终事实源。

不适用的章节保留简短说明，写清不适用原因，不用空模板充数。

## 7. 核心链路标准

一条核心链路至少回答：

1. 谁在什么场景触发链路。
2. 入口路由、命令、事件或 UI 操作是什么。
3. 输入在哪里解析、校验和授权。
4. 业务决策由哪些模块和符号承担。
5. 数据在哪里读取、转换和持久化。
6. 外部服务、模型、缓存或消息系统在哪里参与。
7. 状态如何变化，幂等性和事务边界在哪里。
8. 最终输出如何构造并呈现给用户。
9. 失败、超时、重试、降级和回滚如何处理。
10. 哪些测试覆盖了该链路，哪些部分仍未覆盖。

每篇核心链路必须同时包含顺序图、关键节点表、代码阅读顺序、失败路径和验证方法。

## 8. 代码精读标准

核心代码选择依据是链路关键性、业务决策密度、状态变化、外部边界或高修改风险，而不是文件长度。每个精读对象说明：

- 路径与符号。
- 存在目的和职责边界。
- 调用者与被调用者。
- 输入、输出、副作用和状态变化。
- 关键分支、不变量和边界条件。
- 框架生命周期或配置影响。
- 修改影响范围。
- 初学者常见误解。
- 当前设计的优点、限制和替代方案。

源码片段只保留理解所需的最小范围，优先引用路径和符号，不复制完整文件。

## 9. 图表标准

- 使用 Mermaid，图后必须有文字解释。
- 系统上下文图突出用户、系统和外部依赖。
- 模块图只画稳定边界，避免把每个文件画成节点。
- 顺序图对应一条具体链路，名称应与代码符号或运行组件一致。
- 图中推断出的连接必须标记 `[I]`，不能用视觉确定性掩盖证据不足。

## 10. 运行与安全标准

- 记录操作系统、运行时、包管理器和关键依赖版本。
- 环境变量只记录名称、用途、是否必需和示例格式，不记录真实密钥。
- 对安装、迁移、清理、写库、上传和外部调用区分只读与有副作用操作。
- 运行命令记录工作目录、前置条件、退出状态和成功信号。
- 无法运行时记录阻塞原因、已尝试动作和静态证据，不伪造运行结果。

## 11. 验收阻断项

以下任一情况存在时，详细版不得标记完成：

- 核心结论没有证据或错误标记为已验证。
- 启动命令未执行却声称运行成功。
- 没有端到端核心链路。
- 只按目录罗列文件，没有产品或业务主线。
- 没有失败路径、异常处理或边界条件。
- 架构图与代码路径无法对应。
- 面试指标、性能提升或业务成果没有可追溯来源。
- 练习没有成功判定方法。
- 文档泄露密钥、个人数据或真实敏感配置。

## 12. 简洁版派生规则

简洁版优先级低于详细版。只有 G6 通过后才能生成，且必须：

- 只使用详细版已有结论和证据。
- 保留最关键的未知项和限制。
- 不新增技术指标、设计理由或面试表述。
- 在文首记录来源详细版的版本或提交。
