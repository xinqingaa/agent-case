# 证据模型

版本：0.2.0
状态：0.2 已冻结

本文件约束 Agent 如何采信结论。学习文档不要把这些标记当作读者必修；读者看到的应是项目事实，以及路径、模块或命令等定位信息。证据 ID 写在 `EVIDENCE.md`。

## 结论状态

| 标记 | 含义 | 最低要求 |
|---|---|---|
| `[R]` | 运行验证 | 有命令或操作、环境、结果和成功/失败信号 |
| `[V]` | 静态验证 | 有精确源码、配置、测试或历史位置 |
| `[C]` | 用户确认 | 有确认内容、适用范围和日期 |
| `[I]` | 合理推断 | 有间接证据，并说明验证方式 |
| `[U]` | 未知 | 说明缺失信息和下一验证动作 |

## 证据强度

针对实现行为，通常依次优先：可重复运行观察、带断言的测试、当前源码与配置、版本历史、现有项目文档、用户确认的意图、命名或不完整材料推断。意图与实现冲突时同时记录，不能静默选择。

## 证据 ID

- `E-BOOT-*`：环境、构建、启动和健康。
- `E-PROD-*`：用户、场景和产品行为。
- `E-ARCH-*`：系统边界和依赖。
- `E-FLOW-*`：端到端执行链路。
- `E-DATA-*`：数据、状态、持久化和事务。
- `E-TEST-*`：测试和质量检查。
- `E-RISK-*`：安全、性能、缺陷和债务。
- `E-USER-*`：用户确认的背景、意图或贡献。
- `E-OPEN-*`：问题、矛盾和待验证项。

证据一旦被文档引用，不应随意重新编号。

## 引用精度

源码证据优先定位到路径加符号、配置键或测试名。命令证据必须记录 cwd、前置条件、命令、退出状态、结果摘要和副作用。仓库根目录、大文件或含糊的“见源码”不是精确证据。

## 指标

任何性能、质量或业务数字都必须包含指标定义、数据集或负载、测量方法、环境、结果和日期。信息不足时只能标记为用户声明或未知，不能作为已验证事实。

## 一致性检查

验收前必须比较产品步骤与核心链路、架构节点与路径、启动命令与实际环境、数据模型与状态变化、面试声明与证据、练习与成功信号。冲突必须进入证据台账和阻断项。
