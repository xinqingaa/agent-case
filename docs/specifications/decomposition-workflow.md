# 项目拆解工作流

版本：0.3.0
状态：0.3 设计中

## 总则

拆解从用户和产品链路开始，以可追溯实现、运行观察和学习验证结束。阶段门不是写作目录；未满足当前阶段的退出条件时，不进入下一阶段。

阶段编号是 Agent 工序。向用户汇报时用白话：现在要读源码、现在要本地跑、已经搞清什么、还卡在什么。不要要求用户学习阶段码、能力字段名或证据 ID。用户只需回答可否读源码、可否本地运行、可否联网；Agent 据此填写 `project.yaml`。

## P0：上游规范

冻结本项目采用的平铺文件命名、学习目标字段、条件式交付和验收规则。此阶段不读取任何项目源码。

## P1：范围与授权

- 确定项目 ID、名称、源码路径、源码 revision 和目标读者。
- 用用户的白话许可填写授权等级、能力矩阵、排除目录和禁止操作。
- 记录本轮问题、交付状态和不做事项。
- 初始化工作区，但不读取源码内容。

退出条件：`project.yaml` 足以约束下一步行为；所有未明确能力保持禁止。

## P2：项目侦察

在授权范围内识别：

- 清单、运行时约束、入口和配置候选。
- UI、API、CLI、任务、事件或库接口等产品入口。
- 主要进程、稳定模块和外部边界。
- 测试位置、生成目录和排除区域。
- 候选产品链路、核心链路、未知项和矛盾。

先宽后窄，使用清单、入口、符号搜索、调用点和测试缩小阅读范围。侦察记录进入 `working/`，可引用证据同时进入 `EVIDENCE.md`。

## P3：事实底座

形成产品、用户链路、架构、数据状态、核心流程、接口、测试和风险的最小事实集合。文件名使用 `foundation-` 前缀并保持工作区平铺。

## P4：运行基线

只有相应能力为 `true` 时才执行。按低副作用到高副作用推进：

1. 记录操作系统、运行时和工具版本。
2. 验证依赖准备方式。
3. 执行编译、类型检查或构建。
4. 启动最小依赖模式并观察健康信号。
5. 执行离线测试。
6. 验证核心 API、CLI 或 UI 场景。
7. 在额外授权下读取数据或访问外部系统。

每条命令记录 cwd、前置条件、退出状态、成功或失败信号、副作用和证据 ID。进程未退出不等于启动成功。

## P5：学习路线

按 `project.yaml` 的目标档案生成 `source-study-*`、`replication-*` 和 `extension-*`。排除项不得伪造为必修内容。

## P6：验收

- 描述角色、目标、输入、输出和用户可见失败。
- 将产品步骤映射到真实入口和组件。
- 先建立系统上下文，再建立模块与运行时视图。
- 架构模式只有在直接证据支持时才使用；否则描述观察到的边界和依赖方向。

## G4：核心链路

按产品价值、架构覆盖、业务决策、状态变化和学习价值选择 1 至 4 条链路。每条链路必须覆盖触发、入口、校验、业务逻辑、数据变化、外部调用、输出、失败、重试或降级、测试和验证方法。

## G5：专题与学习设计

按项目适用性分析接口、数据、配置、测试、调试、安全、性能和技术债。把稳定事实转化为前置知识、术语、模块地图、业务思路、可判定练习和准确表达。不要写成函数精读课或纯前端实现教程。

## G6：验收

执行机械检查、事实检查和学习检查。交叉核对产品步骤、架构节点、路径、符号、数据变化、命令、证据、练习和面试声明。阻断项未通过且未获得窄范围豁免时，不得声明完成。

## 交付状态

- `draft`：仍在调查或写作。
- `static-reviewed`：静态事实和学习结构已审阅，但没有完整运行验证。
- `runtime-verified`：授权范围内的运行基线和代表性场景已验证。
- `accepted`：声明的交付目标通过 P6。

`static-reviewed` 可以成为有价值的阶段产物，但不能声称启动、测试或运行行为已经验证。
