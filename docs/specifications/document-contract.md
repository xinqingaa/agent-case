# 项目学习文档契约

版本：0.3.0
状态：0.3 设计中

项目交付不是固定篇数的文章集合，而是由事实底座派生出的学习系统。所有项目都经过同一套证据工作流，但学习内容按项目目标选择。项目工作区必须完全平铺，不使用二级目录；文件名前缀表达内容类型。

```text
事实底座 → 源码学习路线 → 最小复刻路线 → 扩展与二次开发 → 跨项目比较
```

事实底座是唯一事实源，后续路线只能引用它，不能新增未经核实的项目行为。

```mermaid
flowchart LR
    Product[01-02 产品] --> System[03-06 环境与架构]
    System --> Data[07 数据与状态]
    Data --> Flow[08 核心链路]
    Flow --> Thinking[09 业务能力与思路]
    Thinking --> Quality[10-12 集成、测试、风险]
    Quality --> Learn[13-14 练习与表达]
    Learn --> Guide[00 学习导航最后回填]
```

## 读者画像与省略规则

默认读者是「有工程背景、但不是这个仓库作者的人」。项目陌生不等于技术小白。

| 维度 | 默认假设 | 写作要求 |
|---|---|---|
| 前端 | 深厚 | 不写组件、样式、框架用法等实现教程；不罗列纯前端知识 |
| 后端 | 概念级 | 写这个项目里后端负责什么、数据怎么走、接口契约、失败如何回传；不写「什么是 REST/SQL」 |
| AI / LLM / RAG | 概念初学者 | 只在本项目真正用到时，用项目模块和链路解释；不单独开课 |
| 学习重点 | 协作与思路 | 前后端边界、前端参与到哪一层、系统怎么串、AI-native 如何调试 |
| 深度 | 按需 | 默认克制；读者点名再展开某一层 |

「零基础」只表示「不是该项目的作者」，不表示需要从编程基础讲起。

## 学习面与后台

| 读者读的学习面 | Agent 自己用的后台 |
|---|---|
| 平铺学习文件（`foundation-*` 等）、`GLOSSARY.md` | `project.yaml`、`EVIDENCE.md`、`ACCEPTANCE.md`、`working/` |
| 用路径、模块、命令定位事实 | 用证据 ID 和 `[R]/[V]/[C]/[I]/[U]` 约束采信 |
| 白话说明「已核对源码 / 已实际跑过 / 还没验证」 | 阶段门 P0–P6、能力矩阵 |

向用户汇报时说明：现在在做什么、需要哪一种许可、已经搞清什么、还卡在什么。不要要求用户学习阶段码或证据字母表。用户只需回答可否读源码、可否本地运行、可否联网；Agent 据此填写 `project.yaml`。

学习文档的表格不要为了引用去堆 `[V][E-ARCH-001]`。需要定位时写路径、符号或命令。证据台账仍由 Agent 同步维护。

## 平铺交付集合

| 文件 | 核心问题 | 要求 |
|---|---|---|
| `foundation-*.md` | 产品、链路、架构、数据、接口、测试和风险 | 所有项目按适用性完成 |
| `source-study-*.md` | 按概念理解源码、Agent loop、工具、状态和取舍 | `source_study` 为 required 时完成 |
| `replication-*.md` | 从零实现核心价值的最小闭环 | `minimal_replication` 为 required 时完成 |
| `extension-*.md` | 工具、路由、模型、记忆、协议和工作流扩展 | `extension_development` 为 required 时完成 |
| `comparison-*.md` | 与其他项目比较并提炼通用模式 | 有两个以上项目和明确需求后生成 |

项目根还必须包含 `project.yaml`、`EVIDENCE.md`、`GLOSSARY.md`、`ACCEPTANCE.md`。临时记录使用 `working-*.md`，不得作为事实源。

每个项目在 `project.yaml` 中声明学习目标。排除的路线不生成、不验收；所有项目仍必须完成最小事实底座。

## 单篇共同要求

每篇开头说明前置知识、阅读目标、预计时间和当前把握；正文用路径、模块或命令定位非平凡结论；结尾说明完成判定、未知项和下一篇。主题不适用时保留简短说明，不用空模板充数。

## 核心链路要求

每篇 `08` 必须包含触发与结果、顺序图、关键节点表、数据或状态变化、失败/重试/降级、测试覆盖、关键节点顺序和验证方法。节点顺序用来跟上一条链路，不是函数精读课。

## 业务能力与思路要求

`09` 解释项目能办成什么、关键业务如何裁决、默认思路是什么、前端参与到哪一层、以及常见想错的方式。不要写符号精读、调用者/被调用者或实现教程。Agent 仍可把源码当核实材料，但正文面向业务与协作。

与相邻篇的分工：`01` 是产品定位，`02` 是用户步骤，`07` 是概念和数据，`08` 是一条路径怎么跑，`09` 是业务上怎么想、能力怎么切、决策在哪一侧，`12` 是风险和代价。

## 横向一致性

产品链路变化必须同步检查架构、核心链路、思路、练习和表达；运行变化同步检查运行手册、测试、证据和验收；数据变化同步检查核心链路、思路和风险；外部接口变化同步检查架构、运行手册、测试和风险。

## 简洁版

只有详细版通过相应 P6 后才能派生简洁版。简洁版不得新增事实、指标、设计理由或个人贡献。
